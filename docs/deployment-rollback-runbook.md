# Eureka deployment and rollback runbook

## Boundaries

This service is localhost-only and does not change `/etc/asterisk/pjsip.conf`. Phase 1 routing is documented in `phase-1-baseline-and-blocker.md`; do not edit a live dialplan without its backups and authorized operator. Provider credentials belong only in `/etc/eureka/eureka.env` (owner `root:eureka`, mode `0640`) and must never enter this repository, logs, or systemd unit.

## Deploy

1. Create an unprivileged `eureka` user and install the repository below `/opt/eureka`; create `/var/log/eureka` as `eureka:eureka`, mode `0700`. Use Python 3.11 or newer and create the unit's Python environment with `python3 -m venv /opt/eureka/venv`, then install the declared dependencies with `/opt/eureka/venv/bin/pip install -r /opt/eureka/requirements.txt`.
2. Copy `.env.example` to `/etc/eureka/eureka.env` and use only `EUREKA_HOST=127.0.0.1`. Set a short `EUREKA_LOG_RETENTION_DAYS` (default 7). The default `EUREKA_PROVIDER_MODE=disabled` preserves the Phase 2 unavailable fallback. To enable Phase 3, set `EUREKA_PROVIDER_MODE=live`, `EUREKA_TTS_PROVIDER=elevenlabs`, an OpenRouter Anthropic Haiku model ID (for example `anthropic/claude-haiku-4.5`), an ElevenLabs voice ID, and the three provider keys in the protected environment file. The old `legacy` selection also means ElevenLabs; `kokoro` and other removed selections fail startup rather than switching automatically. STT is Deepgram, AI is routed through OpenRouter to an Anthropic Haiku model, and TTS is ElevenLabs. `EUREKA_HAIKU_API_KEY` now requires an OpenRouter API key, not a direct Anthropic key; check model availability and account billing before enabling. Optional model, endpointing and timeout settings are listed in `.env.example`. Missing or invalid live configuration must not silently enable an unsafe substitute.
3. Before enabling providers, obtain authorization and review each provider's data handling and retention settings: caller audio is transmitted to Deepgram, validated text and limited context to OpenRouter and its selected downstream model provider, and checked response text to ElevenLabs. Review OpenRouter routing, provider privacy and retention policies, and any account-level restrictions; the local service does not control upstream retention or routing. The local service does not persist raw audio. Do not use real caller data in unapproved tests.
4. Copy versioned `prompts/system-v1.txt`, `prompts/system-v2-general.txt`, and `knowledge/approved-facts-v1.json` to the configured read-only paths. Review any knowledge or prompt change before deployment. General answers are enabled by default, but remain unverified and require controlled safety validation and separate deployment approval. The legacy `EUREKA_GENERAL_KNOWLEDGE_ENABLED=false` setting restricts answers to approved facts and does not meet the current MVP general-answer requirement. Approved-fact matching remains narrow and generated replies for matched facts must match exactly. Web search stays disabled unless separately approved and configured. When enabled, search-derived answers are best-effort and may be spoken without citations; search results are not independently verified for accuracy, support, or freshness. Lookup failures receive the lookup-unavailable response. See `general-knowledge-experiment.md` for limitations.
5. In live provider mode, the greeting and feedback prompt are synthesized using the configured ElevenLabs voice; each adds a provider request, latency and usage cost. If synthesis fails, the existing local fallback is played and the call continues; the failure is recorded without provider response text. Those older fallback clips in `phrases/` were rendered with eSpeak and may sound robotic. To replace them and pre-render the thinking prompt in the configured ElevenLabs voice, run `/opt/eureka/venv/bin/python tools/pre_render_phrases.py /opt/eureka/phrases` with the protected provider configuration loaded, then validate with the same command plus `--validate-only`. This makes provider requests and incurs usage cost. If `thinking.slin` is absent in live mode, the service generates it in memory with the configured voice at startup; if that fails, the call continues without a thinking prompt. After recognition, Eureka plays the thinking prompt before weather requests, current-information searches, and general questions of at least 12 words; these are heuristics and may not identify every slow request. Other responses still get the prompt after two seconds of generation or synthesis. The prompt plays at most once per turn. On caller inactivity, the goodbye is synthesized with the configured voice; if synthesis fails, the call ends without a substitute voice. Disabled provider mode does not generate the thinking clip. Listen and verify the clips on a controlled phone before acceptance. The daemon never stores call audio.
6. Install `deploy/systemd/eureka.service`, then run `systemctl daemon-reload`, `systemctl enable --now eureka`, and `systemctl status eureka`. Confirm `ss -ltn` shows `127.0.0.1:9092`, never a non-loopback address.
7. Run every pending item in `phase-2-4-validation.md` on a controlled phone/softphone. Inspect `journalctl -u eureka` and protected JSONL logs for component outcomes and redacted transcripts only. Review feedback together with controlled-test outcomes before updating knowledge, prompts, or safety tests.

## Health and retention

The service is healthy when systemd reports it running and the bound listener is loopback-only. Logs are JSONL in `EUREKA_LOG_DIR`; the service restricts the directory to mode `0700` and log files to `0600`, and purges files older than `EUREKA_LOG_RETENTION_DAYS` (default 7) at startup, on each write, and hourly while the service is running. When the service is stopped, arrange an authorized scheduled purge as needed. Transcripts are fully redacted locally; component names and operational outcomes are retained. Never copy raw audio or caller number records into tickets.

## Rollback

1. `systemctl disable --now eureka`; verify no listener remains on port 9092.
2. Remove only the Phase 1 additive include, the `from-internal` include entry, and `/etc/asterisk/eureka-extensions.conf`; run `asterisk -rx 'dialplan reload'`. Use the fresh pre-change backup only if this exact reversal cannot restore the baseline.
3. Verify `dialplan show 0` no longer selects Eureka and repeat existing outbound, HT802 registration, and VoIP.ms inbound/outbound regression calls.
4. Preserve protected operational logs only for their configured retention period; do not retain raw audio.

## Optional AMI feedback (separate deployment approval required)

Asterisk 18's `AudioSocket()` application forwards audio, not keypad events. The optional AMI client uses the versioned dialplan's `EurekaAudioSocket` UserEvent to associate the AudioSocket UUID with the channel Uniqueid, then accepts only inbound `DTMFEnd` 1 or 2 during the feedback prompt/window. It is disabled by default; the existing AudioSocket DTMF path remains supported. No live configuration or service restart is authorized by this repository change alone.

Before deployment, approve and test an AMI account restricted to loopback (`127.0.0.1:5038`) with `read = user,dtmf`, **no write permissions**, and the following legacy event filters, subject to verification against the deployed Asterisk 18 build and its exact event formatting/context:

```ini
; In a dedicated manager account, not a complete manager.conf.
deny = 0.0.0.0/0.0.0.0
permit = 127.0.0.1/255.255.255.255
read = user,dtmf
write =
; Adjust the context only after verifying the actual controlled call context.
eventfilter = Event: DTMFEnd[[:space:]].*Context: (from-internal|eureka-operator)[[:space:]].*Exten: 0[[:space:]]
eventfilter = Event: UserEvent[[:space:]].*UserEvent: EurekaAudioSocket[[:space:]]
```

Verify Asterisk's listener bind, account IP ACL, event permissions, filter semantics, and the actual context and extension on controlled calls before enabling. A route reached through a dialplan include may retain the originating context rather than `eureka-operator`; the example includes `from-internal` but must be narrowed to the observed route. Filters are include alternatives, not cumulative; incorrect expressions can suppress required events or admit other calls. The DTMF filter can include unrelated calls to extension 0 in the selected contexts. AMI events contain caller and connected-line metadata, and AMI is **not** inherently restricted to Eureka calls. Validate that these filters exclude other-call events on the deployed version; do not log or capture raw event streams while testing. The client discards irrelevant fields and does not log AMI messages, credentials, channel identifiers or non-rating digits. Use a dedicated nonprivileged account and protected environment file for `EUREKA_AMI_USERNAME` and `EUREKA_AMI_SECRET`; set `EUREKA_AMI_ENABLED=true` only after approval. Credentials must not contain newlines.

Install the versioned correlation event and enable the client together under the existing controlled-change and rollback procedure. Check feedback 1 and 2 on separate controlled calls and regression-test the audio path; unit tests do not establish actual Asterisk behavior. With this least-privilege account, Hangup events (class CALL) are normally unavailable; AudioSocket cleanup removes active mappings and unmatched mappings expire. A disconnect clears all mappings and reconnects with bounded backoff; calls already in progress cannot be re-correlated, so their AMI feedback is lost rather than guessed. New calls can correlate after reconnection. Roll back by disabling AMI in the protected environment, removing the dedicated account and versioned UserEvent from the deployed dialplan using the approved procedure, and restoring the prior service and dialplan configuration. Do not perform these actions without approval.
